# R224 — Windows releases signed through SignPath Foundation

<!-- status: open -->

**Open, and blocked on SignPath** (§ 3). Chosen by the project lead for 1.2.2 over the Microsoft Store,
after a comparison of the two routes.

## 1. Why, and why SignPath

- **Smart App Control blocks Klados outright today.** Microsoft: *"unknown, unsigned code are blocked
  by default"*, and a blocked app has no "run anyway". It turns itself on for most clean Windows 11
  installs. A certificate from a CA in the Trusted Root Program lets an app run where Microsoft's
  cloud service has no verdict on it.
- **SmartScreen** keeps warning about any new file until reputation builds; EV certificates lost
  their instant pass in 2024. Signing replaces "Unknown publisher" with a name, and lets reputation
  accumulate across releases signed under one identity.
- **Integrity:** Windows checks the signature itself, which is stronger than a `SHA256SUMS.txt` few
  people verify.

**Why SignPath and not the alternatives:**
- It is free.
- Its certificate names **SignPath Foundation** as publisher, which keeps the project lead's legal
  name off every download, in line with the pseudonymous identity R140 and R172 froze.
- The installer, R219's "Open with" registration and the settings location stay exactly as they are.
- The alternatives lose on one of those:
  - *Azure Artifact Signing* issues certificates to individuals only in the USA and Canada.
  - An *OV certificate* carries the holder's legal name.
  - *The Store* is a second packaging track that rebuilds "Open with" and moves settings; it stays an
    option for later.

## 3. To settle before building — the round cannot start without these

1. **Acceptance.** The project applies at signpath.org, and only the project lead can: it needs an
   account in their name. Their terms, which Klados meets as far as can be read:
   - an OSI licence without commercial dual-licensing (MIT);
   - no proprietary components;
   - actively maintained and already released;
   - functionality described on the download page (the README).
2. **Team names on the policy page.** SignPath requires a published code-signing policy listing team
   members' roles and "names". Ask whether the GitHub handle `mincowski` is enough.
3. **Which files may be signed.** Their terms: signers sign only *"software artifacts built from their
   own source code"*.
   - `Klados.exe` is Electron's binary with rewritten resources. Other Electron projects sign it
     through SignPath, but ask rather than assume.
   - Electron's four DLLs and electron-builder's `elevate.exe` are not built from Klados's source.
4. **Does Smart App Control accept the unsigned DLLs?** It checks every binary, not only the one
   launched. If Electron's DLLs cannot be signed (point 3), the question is whether Microsoft's service
   already knows their exact files. They are byte-identical across every app on Electron 44.4.5, so it
   plausibly does, but that is a guess.
   - **Measured, not assumed:** a fresh Windows 11 virtual machine, with Smart App Control switched
     from evaluation to on, running a build signed with SignPath's test certificate.
   - If the DLLs are blocked, signing alone does not deliver § 1's main benefit. Report that before
     building further.
5. **How many approvals per release** (§ 4). SignPath Foundation requires a manual approval for every
   release, so the number of signing requests per release is a cost the project lead pays each time.

## 4. The mechanism — to be confirmed against SignPath's documentation in the round

Today the Windows job in `release.yml` builds and publishes in one `electron-builder` call, and
nothing is signed. With SignPath the order must become:

1. **Build the unpacked app** (`--dir`).
2. **Sign `Klados.exe`** through a SignPath signing request from GitHub Actions, then wait for the
   approval.
3. **Build the installer from the signed files** (`--prepackaged`), and sign the installer and the
   uninstaller. electron-builder signs the uninstaller while it builds the installer, through its
   `sign` hook, so this may be a second and third request unless SignPath's artifact configuration can
   combine them. **Fewest approvals wins; the target is one per release.**
4. **Publish, then `checksums`.** The checksums job already runs after the release jobs and hashes
   what was published, so it hashes the signed files without change.

**Also part of the round:**
- **CI fails if a signature is missing.** A step checks `Get-AuthenticodeSignature` on `Klados.exe`,
  the installer and the uninstaller.
- **Waiting for approval does not break the timeout (R192).** The Windows job is capped at 30
  minutes, and a wait for a human approval can exceed it. The wait gets its own job and timeout,
  rather than raising the cap on the build.
- **Rehearsals (`workflow_dispatch`, D-095) should not need a release approval.** SignPath offers
  test-signing policies with a test certificate, and a rehearsal uses that.
- **The project side:**
  - a `docs/CODE-SIGNING.md` policy page, with SignPath's required attribution (*"Free code signing
    provided by SignPath.io, certificate by SignPath Foundation"*), the team roles, and a privacy
    statement (Klados sends nothing anywhere);
  - MFA on GitHub and SignPath for every team member;
  - the README's "not signed" paragraph updated for Windows (macOS unchanged).

## 5. Non-functional

- **Releases wait for a person.** A tagged release produces nothing publishable until the project
  lead approves the signing request. The draft release makes that visible rather than silent.
- **Size and behaviour of the app are unchanged**; signing adds a few kilobytes per file.

## 6. Not in this round

- macOS signing and notarization (Apple Developer Program), the Microsoft Store, and winget.
